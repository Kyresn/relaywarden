# 推理回放（replay）

## Problem Statement

用 Chat Completions 客户端（各类 CLI agent、IDE 插件）通过 RelayWarden 接到 Codex Responses 上游时，模型上一轮的推理载荷在往返中丢失。

上游以 `store: false` 运行，服务端不留对话状态，唯一的跨轮载体是响应里的 `encrypted_content`。客户端不理解这个字段，把它丢在历史之外；下一轮请求里就没有 reasoning item。上游每轮从零开始推理，输出 token 变多、单步变慢，多步任务的完成率下降。

用户看到的后果：同一个模型、同样的题，经过本插件转发时明显比直连慢，且更容易在长任务上跑偏。用户无法自行修复——客户端协议里没有放推理载荷的位置，这不是配置问题。

## Solution

插件在服务端保存推理载荷，在返回给客户端的助手内容里留下一个不可见标记；客户端下一轮回传历史时，插件在翻译成上游格式之后把标记还原成 reasoning item，并删掉标记。

对用户而言：不需要换客户端、不需要改客户端代码、不产生额外上游请求。开启 `replay` 后，多轮请求自动带上历史推理。标记是 HTML 注释，客户端界面上不显示。

## User Stories

1. 作为使用 Chat Completions 客户端的用户，我希望开启回放后多轮对话自动携带上一轮推理，这样模型不必每轮重新推理。
2. 作为用户，我希望回放不需要我更换客户端或修改客户端配置，这样我可以用任何兼容 OpenAI 协议的客户端。
3. 作为用户，我希望回放不产生额外的上游请求，这样我的额度消耗不会因为开启回放而上升。
4. 作为用户，我希望回放标记在客户端界面上不可见，这样我的对话记录不会出现奇怪的符号。
5. 作为用户，我希望回放标记不破坏客户端的 Markdown 渲染，这样即使客户端渲染了标记也不会乱版。
6. 作为用户，我希望只有工具调用、没有文本内容的助手轮也能被回放，这样连续工具调用的长任务不会在中间断链。
7. 作为用户，我希望同一个会话里多轮推理能逐轮累积，这样长任务的上下文保持连贯。
8. 作为用户，我希望回放条目有有效期，这样过期的推理不会无限期占着我的存储。
9. 作为用户，我希望存储有总量上限，这样长期运行不会把磁盘写满。
10. 作为用户，我希望超过上限时优先淘汰最旧的条目，这样最近几轮的推理总能命中。
11. 作为运维者，我希望回放可以整体关闭，这样出现问题时能一键止损。
12. 作为运维者，我希望回放可以只对非流式请求生效，这样在流式链路有问题时仍能保留部分收益。
13. 作为运维者，我希望回放可以只对流式请求生效，这样我能对比两种链路的表现。
14. 作为运维者，我希望存储可以选 Postgres，这样多实例部署时回放条目能共享。
15. 作为运维者，我希望存储可以退回内存，这样没有 Postgres 的环境也能先试功能。
16. 作为运维者，我希望没有配置 Postgres 时自动降级到内存而不是启动失败，这样试跑不会因为缺依赖卡住。
17. 作为运维者，我希望降级到内存时管理界面明确显示当前是内存模式，这样我不会误以为条目是持久化的。
18. 作为运维者，我希望内存模式重启后条目丢失能被文档说明，这样我不会把它当成 bug 报。
19. 作为运维者，我希望回放不依赖宿主的数据库连接，这样插件不要求宿主提供它并不提供的配置。
20. 作为运维者，我希望回放条目的 DSN 由插件自己的配置给出，这样我能把它指向独立的库。
21. 作为运维者，我希望 `enabled` 打开但流式与非流式都关时配置校验直接报错，这样我不会以为功能开了其实没开。
22. 作为运维者，我希望选择 Postgres 但 DSN 为空时配置校验直接报错，这样我不会在不知情的情况下跑在内存模式。
23. 作为运维者，我希望回放只对 Responses 上游生效，这样其它格式对的转发行为完全不变。
24. 作为运维者，我希望注册回放钩子后其它格式对的请求体原样返回，这样引入回放不会改变现有链路的行为。
25. 作为运维者，我希望回放钩子内部任何异常都不阻断请求，这样回放的问题不会变成用户的 502。
26. 作为运维者，我希望回放失败时请求照常转发，这样功能可用性永远高于回放收益。
27. 作为运维者，我希望客户端重试同一请求时不会重复注入推理，这样重试不会让上游收到畸形历史。
28. 作为运维者，我希望同一请求里重复出现的引用只展开一次，这样重复标记不会产生重复 reasoning item。
29. 作为运维者，我希望查不到的引用只删标记、不报错，这样历史被截断或库被清空后请求仍能正常进行。
30. 作为运维者，我希望格式不合法的标记也只删不报错，这样伪造或损坏的标记不会造成请求失败。
31. 作为运维者，我希望回放关闭时不主动清理客户端历史里的旧标记，这样开关来回切换不会损坏历史。
32. 作为运维者，我希望客户端把 HTML 注释剥掉时功能静默退化而不报错，这样不兼容的客户端仍能正常使用。
33. 作为运维者，我希望通过命中率发现客户端剥离注释的情况，这样我能定位「功能开了但没效果」的原因。
34. 作为运维者，我希望管理界面显示还原成功次数，这样我能判断功能是否真的在工作。
35. 作为运维者，我希望管理界面显示无效标记次数，这样我能发现历史被污染或库被清空。
36. 作为运维者，我希望管理界面显示生成标记次数，这样我能区分「没生成」和「生成了但没还原」。
37. 作为运维者，我希望管理界面显示当前已存字节，这样我能预判何时触发淘汰。
38. 作为运维者，我希望概览页显示命中率，这样我不用心算两个计数。
39. 作为运维者，我希望回放不单独占一个管理页面，这样界面不会为一个小功能膨胀。
40. 作为运维者，我希望管理界面不展示会话明细，这样会话指纹不会被摆到界面上。
41. 作为运维者，我希望条目绑定签发作用域指纹，这样别的上游或别的凭据签发的推理不会被灌回来。
42. 作为运维者，我希望拿不到凭据身份时明确标记为弱作用域，这样我知道这批条目的隔离强度更低。
43. 作为运维者，我希望上游拒绝回放时被单独分类并记住，这样同一作用域不会每轮反复撞同一面墙。
44. 作为运维者，我希望拒绝记忆只存在进程内、重启清空，这样它的行为边界可预期。
45. 作为运维者，我希望只展开本插件自己签发的条目，这样客户端历史里混入的同类标记不会被误展开。
46. 作为运维者，我希望外来条目、失效条目、被抑制条目分别计数，这样我能分清三种失败原因。
47. 作为安全审阅者，我希望文档写明回放库包含推理明文、应按凭据等级保护，这样部署者知道该库的敏感级别。
48. 作为安全审阅者，我希望回放不做应用层加密但被明确声明，这样我不会误以为库是加密的。
49. 作为开发者，我希望回放条目存储有一层抽象，这样 Postgres 与内存两个实现共享同一套调用方。
50. 作为开发者，我希望回放引用的长度固定，这样扫描与提取标记的实现足够简单。
51. 作为开发者，我希望回放引用的前缀固定且不开放配置，这样标记格式不会因配置漂移而互不兼容。
52. 作为开发者，我希望一个回放引用对应一整轮助手输出，这样还原逻辑不需要处理块级拼接。
53. 作为开发者，我希望回放相关的计数与现有指标共用同一套计数设施，这样不需要新开统计通道。
54. 作为开发者，我希望回放出的 reasoning item 出现在 assistant 消息项之前，这样与上游的位置约定一致。

## Implementation Decisions

### 挂点

- **还原**：`RequestNormalizer.NormalizeRequest`。该钩子在原生翻译之后执行，拿到的是最终上游 payload，并带 `FromFormat`、`ToFormat`、`Model`、`Stream`、`Body`。
- **捕获**：`ResponseBeforeTranslator.NormalizeResponse`。该钩子在响应翻译之前执行，此时上游原始响应体里的 `encrypted_content` 仍然可见。
- **明确不用** `request.intercept_after`：该钩子的 `Body` 仍是源协议 JSON，真正的 provider payload 在 executor 内部翻译，无法在此注入 Responses 格式的 reasoning item。
- 插件注册的 `RequestNormalizer` / `ResponseBeforeTranslator` 是追加，不是替换；原生转换先执行，再调用插件钩子。
- 还原不需要 `RequestID`：回放引用本身携带定位信息，还原只依赖「body 里有标记 + 库里有条目」。

### 标记形态

- 形式：`<!--rw-replay:<25 位引用>-->`。前缀与长度固定，不开放配置。
- 粒度：一个回放引用对应一整轮助手输出，不做块级拆分。
- 位置：assistant 的 `content` 末尾；`content` 为空或为 null 的 tool-call 轮，把 `content` 写成只含标记的字符串。

### 还原规则

- 仅在 `ToFormat` 为 Responses 且 `replay.enabled` 为真时工作，其它情况原样返回 `Body`。
- 步骤：扫描历史中 assistant 项的内容，提取回放标记，按引用查库，命中的把 reasoning item 插回对应位置，从历史中删除标记，返回新 body。
- 幂等：还原即删标记，同一 body 被上游重试时不会二次注入。
- 重复标记：同一请求内同一引用只展开第一次，其余删除。
- 失败策略：钩子内任何异常都原样返回输入 body（fail-open）。

### 标记合法性三档

- 命中自家条目：展开。
- 引用格式合法但查无条目或已过期：`replay_invalid`，删标记。
- 查到的条目 `owner` 不符：`replay_foreign`，删标记，不展开。

### 签发作用域指纹

- 指纹 = 稳定哈希（`FromFormat`、`ToFormat`、部署标识、凭据身份）；`ToFormat` 为 Gemini 时追加 `Model`。
- 还原时重算指纹，与条目不符即视为外来条目。
- 拿不到凭据身份时退化为只含 `FromFormat` + `ToFormat` 的弱作用域，条目打 `weak_scope: true`，界面单列计数。

### 被拒分类与拒绝记忆

- 上游拒绝推理载荷时分类记录；识别不到稳定特征时退化为失败率对比，只记录不记忆。
- 拒绝记忆：进程内 map，键为作用域指纹，容量 4096，TTL 与条目 TTL 一致，重启清空。
- 命中拒绝记忆：不展开，标记照常删除，计数 `replay_suppressed`。

### 位置规则

- reasoning item 作为独立数组元素，插在该轮 assistant 消息项**之前**。
- 该轮只有工具调用时，插在 `function_call` 项之前。
- 一轮多个 reasoning item 保持原始顺序。

### 捕获规则

- 从上游响应中提取本轮的 reasoning item 数组，生成回放引用，写入回放条目，并在对应 assistant 输出里注入回放标记。
- 非流式：直接改响应体。
- 流式：调用形态待验证。需确认 `ResponseBeforeTranslator` 对流式响应是逐 chunk 调用还是整体调用，以及注入的标记片段能否在 `finish_reason` 之前独立下发。
- 流式验证不通过时的回退顺序：① 只在非流式生效，并在管理界面标明；② 改用 `StreamChunkInterceptor` 在下游 chunk 上补标记——此时上游原始 reasoning 已不可见，需改为旁路捕获，成本更高。

### 存储

- 抽象一层回放条目存储，两个实现：Postgres（`pgx/v5`）与内存。
- 条目字段：引用、`owner`、`FromFormat`、推理载荷数组、签发来源、`weak_scope`、创建时间、过期时间、字节长度。
- 淘汰：TTL（默认 24 小时）加总字节上限（默认 512 MB），超限按最旧淘汰。
- 不复用宿主的数据库连接——插件接口不提供；DSN 由插件自己的配置给出。
- 不做应用层加密；README 必须写明该库内容包含推理明文，应按凭据等级保护。

### 配置

```yaml
replay:
  enabled: true
  backend: postgres       # postgres | memory
  allow_memory_fallback: true
  postgres:
    dsn: ""               # 空 = 不启用 postgres，退回内存
  ttl_hours: 24
  max_bytes: 536870912
  stream: true
  nonstream: true
```

校验：

- `enabled` 为真但 `stream` 与 `nonstream` 都为假：报错。
- `backend` 为 `postgres` 但 `dsn` 为空：报错。
- `backend` 为 `memory` 时不校验 DSN。

### 失败与降级

- 功能关闭：还原与生成都不执行；客户端历史里已有的标记原样保留，不主动清理。
- 无 Postgres：降级到内存模式，功能可用但重启即丢；管理界面必须显示当前模式，不能只写日志。
- 客户端剥离 HTML 注释：静默退化，表现为命中率归零，不报错。

### 指标与界面

- 计数：还原成功、`replay_invalid`、`replay_foreign`、`replay_suppressed`、生成标记、当前已存字节、弱作用域条目数。
- 命中率 = 还原成功次数 ÷ 带标记的请求数。
- 概览页增加一栏：存储模式、命中率、已存字节、无效标记次数、弱作用域条目数。不做独立页面，不展示会话明细。

## Testing Decisions

- 好测试只断言外部行为：给定输入 body，断言输出 body；给定配置，断言校验结果；给定库状态，断言计数变化。不测试内部结构、不测试私有函数、不断言 SQL 文本。
- 唯一测试缝：现有插件方法分发入口 `handleMethod`（`main_test.go:29` 的既有做法）。回放不新增低层测试缝。
- 需要覆盖的行为：
  - 开启且命中：带标记的历史 → 输出含 reasoning item 且标记消失。
  - 位置规则：reasoning item 出现在 assistant 消息项之前，标记是 content 最后一段。
  - 引用查不到：标记被删除，请求正常返回，`replay_invalid` 加一。
  - 作用域不符：`replay_foreign` 加一，不注入。
  - 拒绝记忆命中：第二次同作用域请求不展开，`replay_suppressed` 加一。
  - 同一引用出现两次：只展开一次。
  - 同一 body 处理两次：第二次不再注入（幂等）。
  - 功能关闭：body 原样返回，标记保留。
  - 非 Responses 的格式对：body 原样返回。
  - 配置校验三条。
  - 存储淘汰：超过字节上限后最旧条目消失。
- 测试不连接真实 Postgres、不连接真实上游。存储用内存实现验证行为；Postgres 实现只在编译与接口一致性层面保证，真实库验证留给人工 e2e。
- 指标与界面：只断言计数接口返回值，不断言 HTML 结构。

## Out of Scope

- 非 Responses 上游的推理回放。
- 客户端侧的推理展示或解析。
- 回放条目的应用层加密与密钥管理。
- 跨用户共享回放条目、条目去重、条目迁移。
- 回放条目的导入导出、备份、手动清理界面。
- 会话明细展示、单条条目的查看与调试页面。
- 宿主侧的改动（要求宿主暴露 DSN、要求宿主提供存储接口）。
- 与压缩、守卫、路由、回答风格注入模块的联动策略调整。

## Further Notes

实现前必须先做的七项验证（对应实施计划的 E8）：

1. `ResponseBeforeTranslator` 对流式响应的调用形态：逐 chunk 还是整体。
2. 流式下注入标记片段的时机是否早于 `finish_reason`。
3. 注册 `RequestNormalizer` 后是否影响未启用回放的其它格式对（预期应原样返回，需实测确认）。
4. 25 位引用的库内冲突率与索引设计。
5. 两个钩子是否携带凭据身份或部署标识（决定指纹强度）。
6. 上游拒绝推理载荷时的稳定错误特征（决定被拒分类能否自动识别）。
7. 在 `input[]` 中把 reasoning item 插在 assistant 消息之前，上游是否接受。

另外两项已知缺口：

- 插件注册能力位里目前没有流式相关的声明。若流式回放走 `StreamChunkInterceptor` 回退方案，需先确认该能力位的注册方式。
- `CONTEXT.md` 目前只收录已实现功能的词条。回放相关术语（回放条目、回放引用、回放标记、还原、签发来源、拒绝记忆）在实现落地时补进去。

分支说明：按 `docs/adr/0001-open-source-scope-and-license.md`，推理回放不进入公开主分支，实现应在 `experimental/replay-promptstyle` 分支上进行。本文件写在当前工作区，合入该分支时一并带过去。
