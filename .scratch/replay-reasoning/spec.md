# 推理回放

## Problem Statement

编程客户端走 Chat Completions 经本插件转发到 Codex Responses 上游时，上一轮的推理载荷在往返中被丢掉。上游在 `store: false` 下只能靠 `encrypted_content` 把推理项带到下一轮，字段没带回去，模型每一轮都要重新推理一遍。

后果是可观测的：单步输出 token 更多、耗时更长，在长任务上表现为更容易超时。用户看不到任何报错，只看到「同一个模型经这个转发就是比别家慢、比别家差」。

## Solution

插件在返回给客户端的 assistant 内容里留一个回放标记，把推理载荷存在服务端。客户端下一轮把这段历史原样回传时，插件在发给上游的请求里把标记还原成推理项，并删掉标记本身。载荷按回放条目持久化，带过期与容量淘汰。没配数据库时降级到内存，管理界面明确显示当前模式。

## User Stories

1. 作为使用 Chat Completions 客户端的编程用户，我想要第二轮请求里带上上一轮的推理，以便模型不必从零重新推理。
2. 作为编程用户，我想要回放对客户端完全透明，以便不必更换客户端或改配置。
3. 作为编程用户，我想要标记不会在对话里显示成可见文字，以便它不影响我阅读回答。
4. 作为编程用户，我想要工具调用轮也能回放，以便多步工具循环不重复推理。
5. 作为编程用户，我想要流式响应同样生效，以便我常用的流式客户端也能受益。
6. 作为编程用户，我想要非流式响应同样生效，以便两种调用方式没有行为差异。
7. 作为编程用户，我想要客户端不支持回放时静默退化，以便它不会让我的请求失败。
8. 作为编程用户，我想要过期或无法解析的标记被丢掉而不是发给模型，以便模型不会看到私有格式。
9. 作为编程用户，我想要客户端重复提交同一段历史时只展开一次，以便复制粘贴不会产生重复推理项。
10. 作为运维者，我想要回放条目按 TTL 和总字节上限自动淘汰，以便数据库不会无限增长。
11. 作为运维者，我想要配置了 Postgres 时条目跨重启存活，以便长时间会话不会因为重启丢历史。
12. 作为运维者，我想要没配置 Postgres 时功能降级到内存而不是直接不可用，以便本地开发和单次测试不必先起数据库。
13. 作为运维者，我想要降级状态在管理界面可见，以便我不靠日志去发现「现在是内存模式」。
14. 作为运维者，我想要回放命中率作为指标暴露，以便判断客户端是否真的把标记带回来了。
15. 作为运维者，我想要无效标记计数单独暴露，以便区分「客户端剥离了标记」和「条目被淘汰」。
16. 作为运维者，我想要已存字节数可见，以便在打满上限前调整。
17. 作为插件开发者，我想要回放模块只改请求体、不碰守卫和压缩的既有逻辑，以便两个模块可以独立开关。
18. 作为插件开发者，我想要整个回放功能有独立开关，以便出问题时能一键关掉而不改其它配置。
19. 作为插件开发者，我想要目标不是 Responses 的请求被跳过，以便跨协议场景不会注入错格式。
20. 作为插件开发者，我想要同一个请求被重试时还原是幂等的，以便上游重试不会产生重复推理项。
21. 作为插件开发者，我想要标记前缀和引用长度固定不开放配置，以便不会产生两种互不认的历史。
22. 作为插件开发者，我想要配置校验在启动时就报出「开了功能但没开任何一种传输」这类矛盾，以便错误配置早暴露。
23. 作为安全负责人，我想要库里的内容按凭据等级对待并在文档里写明，以便它不会被顺手放进共享实例。
24. 作为安全负责人，我想要引用不可猜测，以便第三方无法通过构造标记读出别人的回放条目。

## Implementation Decisions

**新模块与边界。** 新增一个回放模块，与守卫、压缩、路由同层。它只做两件事：从客户端历史里识别并移除回放标记、把回放条目里的推理载荷按上游格式插回去；以及在响应下发前生成回放标记。它不改守卫的观察逻辑，也不改压缩对工具输出的处理——压缩只匹配工具输出节点，本模块只匹配 assistant 轮，两者不重叠。

**数据模型。** 回放条目按回放引用索引，字段为：引用、协议格式、推理载荷数组、签发来源、创建时间、过期时间、字节长度。一个引用对应一整轮助手输出，不做块级拆分。

**配置节形状。** 新增 `replay` 配置节，遵循现有约定：节级一个 `enabled`，其余扁平字段——后端选择（postgres 或内存）、允许降级的布尔、Postgres DSN、TTL 小时数、总字节上限、流式开关、非流式开关。校验放在现有的归一化函数里：开启功能但两种传输都关要报错；选了 Postgres 但 DSN 为空要报错。

**固定常量。** 回放标记前缀 `<!--cpa-replay:` 与引用长度 25 位不开放配置，见 ADR-0001。

**还原发生在请求翻译之后。** 插件在凭证选定后收到一份已转换的请求体，此时请求已是上游格式，直接在该请求的输入数组里插入推理项。不在翻译前做，否则要自己模拟一遍转换器。还原时必须同时从历史里删除标记；这样上游重试时同一请求不会二次注入。

**标记生成发生在响应下发前。** 非流式与流式各有一个下发前的改写点。流式需要在结束标记之前单独发出一个携带标记的内容片段；非流式直接改写响应体。流式能力属于当前注册结构尚未声明的能力位，需要补上。

**无效标记处理。** 引用查不到、已过期、或格式不合法时：删除标记，其余历史不动，计入无效标记计数，不报错。

**重复标记处理。** 同一请求内同一引用只展开第一次，后续重复的标记一律删除。

**存储。** 存储抽象为两个实现：Postgres 实现与内存实现。内存实现的过期与上限逻辑与 Postgres 实现一致，只是不持久。插件不尝试复用宿主的数据库连接——插件接口不提供，见 ADR-0002。

**指标。** 新增四个计数：还原成功次数、无效标记次数、生成标记次数、当前已存字节。还原成功次数除以「带推理标记的请求数」即命中率。

**管理界面。** 概览页增加一栏：当前存储模式、命中率、已存字节、无效标记计数。不做独立页面，不展示会话明细。

**开关语义。** 功能关闭时，还原与生成都不执行，已有标记原样留在客户端历史里（不清理），行为与未引入该功能前一致。

## Testing Decisions

**好测试的标准。** 只测外部行为：给定一个请求体和一个响应体，断言输出的请求体/响应体是什么。不测内部结构体、不测数据库 schema、不测私有的辅助函数。测试名描述场景，不描述实现。

**唯一测试缝。** 走插件已有的方法分发入口——测试注册配置、然后以方法名和 JSON 参数调用，断言返回的信封内容。这是现有测试已经在用的最高缝，回放模块不新增更低的缝。

**要测的模块。** 回放模块的全部外部行为都经由上述方法缝覆盖：还原、生成标记、流式片段、降级模式、无效标记、重复标记、幂等重试。存储实现由同一个缝间接覆盖；不做针对 Postgres 的单元测试。

**既有先例。** 主入口测试已有「注册配置 → 调方法 → 断言信封」的写法；压缩与守卫的测试展示了如何用真实的插件请求结构体构造输入。

**配置校验测试。** 沿用现有配置测试的写法：给定一段 YAML，断言归一化是否报错。

**不做的事。** 单元测试不连真实数据库，也不发真实上游请求。需要验证「上游真的收到了推理项」时，用注入的假存储与断言输出请求体来替代，不启动 Postgres 或模型。

## Out of Scope

- Anthropic 的 `thinking` 签名回流与 Gemini 的 `thoughtSignature` 迁移。第一版只针对 Responses 上游。
- 上游拒绝推断文后的「剥离并重放一次」恢复流程，以及按签发来源学习拒绝的记忆。
- 跨账户、跨部署的推理载荷来源判定与剥离策略。
- 管理界面里的会话级明细页。
- 复现那 20 道题的三路对照评测。
- 应用层对载荷加密。
